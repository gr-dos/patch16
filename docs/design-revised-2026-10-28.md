# patch16: exploration and design

**Status:** Proposed / exploratory — no implementation or license decision finalized  
**Target:** Intel 8088/8086, MS-DOS 3.0+ and GR-DOS 4.00  
**Implementation language:** C89-compatible C, limited 8086 assembly only where justified  
**Toolchain:** Open Watcom C; `libc16` as the C runtime  
**Source preference:** Larry Wall's 1988 `patch` 2.0, patchlevel 12, subject to provenance and licensing verification  
**Companion project:** `diff16` (separate; not a prerequisite)

## 1. Summary

Develop a compact, native 16-bit DOS implementation of `patch` based, if legally and technically feasible, on Larry Wall's 1988 source. Preserve as much of Wall's program and its historical identity as practical while adapting Unix assumptions to DOS, constraining memory consumption, and adding **unified-diff support**, using eligible MIT/GPL/Wall-licensed code where appropriate or a clean-room implementation otherwise. The primary use case is accepting textual source-code patches generated by modern `diff -u` and Git on a Linux or other development machine, then applying them to files on an original IBM PC/XT-class system.

A **verified GPL grant is mandatory** for distribution: `patch16` must be redistributable and modifiable for commercial as well as noncommercial purposes under an identified GPL version and its actual applicable terms. Wall's original noncommercial permission is desirable **either** as a verified alternative license for the relevant code **or** as historical documentation, with its restrictions and relationship to the GPL explained accurately. The historical notice must not be presented as granting more rights than it actually grants.

**License boundaries for imported and new code:** `libc16` accepts **MIT-licensed code only**; `patch16` may use code under **MIT, a verified compatible GPL grant, or Wall's original terms where applicable and legally authorized**. Anything from outside the respective allowed license set must be **implemented clean-room from specifications and behavior**, not copied or adapted. New `libc16` contributions stay MIT; new `patch16` contributions must be licensed compatibly with the verified GPL distribution and, if pursuing genuine dual licensing, expressly under both applicable alternatives. Use the MIT-licensed `libc16` without linking the Open Watcom proprietary C runtime. Avoid the `printf` family, particularly formatting and scanning engines, unless evidence shows an unavoidable benefit.

## 2. Goals and non-goals

### Goals

- Run as an ordinary real-mode `.EXE` on an original 8088/8086, without 286+ instructions, DOS extenders, DPMI, protected mode, or expanded/extended-memory requirements.
- Require DOS 3.0+ APIs where practicable; establish the real minimum during porting.
- Apply **unified diffs** from GNU `diff -u` and ordinary textual `git diff` output, as well as Wall's original supported formats where practical (notably context and normal diffs).
- Process files larger than available RAM, using bounded buffers, temporary files, and carefully controlled seeks.
- Handle CRLF versus LF predictably, including patches transferred between Unix and DOS.
- Preserve the original input file on patch failure and avoid silent partial replacement.
- Remain small enough to be useful on floppy-based GR-DOS installations; measure memory footprint and executable size, without declaring an arbitrary binary-size ceiling prematurely.
- Preserve clear original authorship and a file-by-file provenance trail.
- Keep `patch16` independently installable; `diff16` and a network stack are not runtime dependencies.

### Non-goals for the first release

- A full clone of current GNU `patch` options and heuristics.
- Git binary patches, Git index metadata, rename/copy operations, submodules, symlinks, Unix permissions, or timestamps as mandatory semantics.
- Automatic three-way merge or conflict-marker generation.
- Unlimited line length, hunk size, file count, or path depth; limits must be explicit and fail safely.
- Rewriting all of Wall's implementation for stylistic reasons.
- Importing any source authored by Jörg Schilling, whether directly or via a derivative. This is an explicit source-selection constraint.
- Extending `libc16` with a general-purpose `printf`/`scanf` implementation merely to ease the port.

## 3. Historical source and licensing investigation — **release gate**

### 3.1 Baseline candidates

The preferred historical baseline is Wall's `patch` 2.0 at **patchlevel 12 (1988)**, obtainable from a traceable contemporary archive such as the X11R3 source distribution. The archive's actual files, dates, notices, and patchlevel must be inspected and recorded before modification. Do not rely solely on a third-party rehost's repository license badge.

Capture:

1. Canonical source/archive location and its custodian.
2. Archive checksum, original filenames, and unmodified source snapshot.
3. Copyright, copying, README, and documentation notices shipped with that snapshot.
4. Whether files include contributors or code with different terms.
5. A file-by-file inventory identifying original Wall code and any non-Wall components.
6. A comparison against early GNU `patch` snapshots sufficient to explain the licensing chain, **without importing later GNU code by accident**.

The early notice commonly quoted from Wall's source permits copying only if recipients do not attempt to make money from it and do not claim authorship. **The exact notice in the selected archive is the authoritative artifact.** As written, that notice is restrictive and must not be treated as an OSI-approved permissive license.

### 3.2 Mandatory GPL grant; exact version to verify

GNU `patch` documentation says that Larry Wall gave permission for GNU to distribute `patch` under the GNU General Public License. A preserved GNU README from a GPLv2-or-later era includes Wall's 1984–1988 copyright and expressly labels that distribution **GPL version 2 or any later version**. This is good evidence of an authorized GPL lineage, **not by itself a complete chain-of-title analysis for every byte in an independently obtained 1988 archive**.

Before choosing a license identifier or shipping a binary:

- Find the earliest practical GNU `patch` distribution with complete source, README, COPYING, and file headers; document its precise license language.
- Determine whether Wall's permission covers the original 1988 source **as used in `patch16`**, including independent distribution and modification of that baseline, not just redistribution of a specific later GNU package.
- Identify any later contributors' portions included in the chosen baseline and their grants.
- Establish the earliest **provably authorized** GPL version and whether an **“or later”** option was granted. **Do not presume GPLv1-or-later merely because GPLv1 came first, or GPLv2-or-later merely because a later package uses it.**
- Record the result in `docs/LICENSE-RESEARCH.md` with dated primary-source links and the exact notices or bounded excerpts needed to support the conclusion.
- If the evidence does not establish a usable GPL grant for the desired original snapshot, **pause the Wall-based port** and seek explicit permission or choose a separately verifiable Wall-code baseline under the GPL. No release under the original noncommercial permission alone.

**Provisional project policy:** prefer **GPL-2.0-or-later** if the grant is confirmed; otherwise use the actual verified GPL terms (potentially a different minimum version), or do not ship. Modern GNU `patch` uses GPL-3.0-or-later; that newer declaration should not silently be projected backward to the 1988 source.

### 3.3 Treatment of Wall's original notice

There are two acceptable outcomes:

- **Option A — genuine alternative license:** if the rights for the precise Wall-derived material and all other contributors' code support it, publish an accurate expression such as `GPL-2.0-or-later OR <documented-Wall-terms>`. New contributions must explicitly grant both alternatives for the **complete modified program** to be genuinely dual-licensed. If the project cannot grant the Wall alternative for every relevant part, do **not** advertise program-wide dual licensing.
- **Option B — historical artifact (default until proven otherwise):** ship a verbatim, clearly labeled copy or transcription of the historical notice in `docs/HISTORY-LICENSE.md` or within a legally appropriate source archive, credit its original author and context, and clearly state that the operative license of distributed `patch16` is the verified GPL. Merely preserving a historical notice does not automatically confer a second license.

GPL code may generally be distributed alongside separately built MIT-licensed GR-DOS components; their licenses remain distinct. `libc16`'s MIT notices must be retained where required. Ensure the executable, source, patches, required scripts, and license text are supplied in compliance with the **selected GPL version**, not simply labeled “GPL”.

**Legal review:** these are engineering release requirements, not a legal opinion; seek qualified review if the historical license chain remains ambiguous.

### 3.4 Repository-specific provenance and clean-room policy

**The permitted licenses differ by destination repository.** “Clean room” applies to code that cannot be legally reused under that repository's permitted licensing, including code whose licensing or provenance cannot be verified.

| Destination | Existing source that may be reused | New code / fallback |
|---|---|---|
| **`libc16` (library)** | **MIT-licensed code only**, with verified provenance and compatible notices. | Write an **independent clean-room MIT implementation** from specifications and observable behavior; all additions remain MIT. **Never import GPL or Wall-restricted code into `libc16`**, even if it would work technically. |
| **`patch16` (application)** | **MIT**, **GPL under a verified applicable grant**, or **Larry Wall's original licensed code** where its applicable rights are verified. Preserve notices and assess license compatibility and distribution obligations; a historical copy is not automatically GPL-licensed. | Write an **independent clean-room implementation** when other available source is ineligible. New contributions must permit the chosen GPL release; for full-program dual licensing they must also expressly permit Wall's alternative terms. |

In particular, this policy **does not require rewriting already usable MIT or GPL code in `patch16` merely because it was written elsewhere**, and does not allow GPL code into `libc16` merely because `patch16` can use it. Wall-derived portions may be retained in `patch16` only after the rights verification in §3.2. Using MIT code alongside GPL-licensed Wall code normally means complying with both licenses and distributing the combined derivative under the applicable GPL terms; it does **not** automatically turn MIT source files into GPL-only files.

- Do not use Open Watcom runtime source, headers, or disassembled implementations as code templates. Do not copy code with missing, incompatible, or unverifiable permissions. Exclude Schilling-authored sources and downstream changes containing his contributions.
- Separate **reference behavior** from **implementation source**: GNU `patch`, Git, and other tools may be used as black-box test oracles; source reuse requires the repository-specific license and provenance checks above.
- For substantial new modules (for example unified-diff parsing, DOS path conversion, or transactional file replacement), record author/session, specification references, consulted materials, applicable licenses, and tests.
- When a clean-room implementation is needed, the implementer works from published formats, public APIs, behavioral requirements, and black-box tests—not a line-by-line translation of disallowed code. If a separate analyst examines a reference implementation, convey only independent specifications and tests to the implementer.
- Any necessary `libc16` additions must pass its existing runtime-isolation and similarity audits and remain available under MIT terms. Keep `patch16`-specific implementation details in `patch16` rather than expanding the runtime by default.

## 4. Target environment and architecture

### Toolchain and model

- Cross-build on Linux with Open Watcom C and available DOS-compatible assembler/linker as needed.
- Link only against **`libc16`**, with runtime map auditing confirming no Open Watcom C runtime objects or proprietary library dependencies.
- Evaluate small, compact, and large models empirically. Prefer **compact** (small code, far data) if code size and call graph permit; use **large** if necessary, accepting its costs. The original source structure, compiler limits, data sizes, and library ABI will determine the decision.
- All file offsets and sizes must be handled with checked 32-bit arithmetic where DOS and `libc16` support it. Avoid assumptions that `int`, `size_t`, or a near pointer can hold a file size.
- Prefer DOS 3.x-compatible file and directory calls. Do not depend on long-filename APIs.

### Runtime and I/O

- Reuse `libc16`'s `open`, `read`, `write`, `lseek`, `close`, `malloc`, `free`, and basic string/memory facilities where sufficient.
- Investigate `rename`, `remove`/`unlink`, temporary-name generation, file attributes, and 32-bit seeking **before** committing to any `libc16` expansion. A helper may belong in `patch16` if it is too specialized for a general runtime.
- Avoid `printf`, `fprintf`, `sprintf`, `snprintf`, `scanf`, and `sscanf` by default. Use small explicit routines to emit fixed strings, decimal numbers, and filenames with `write`/`fputs` or equivalent; parse numbers with checked digit accumulation. Do not build a general formatting engine for diagnostics.
- Keep the original Wall routines when reasonable, but replace Unix-specific portions through narrow platform adapters rather than spreading `#ifdef` throughout the parser.

### Proposed layers

1. **CLI and option parser:** bounded command line, optional explicit target file, path-prefix stripping, dry-run, output policy.
2. **Diff reader:** buffered line input; identifies normal, context, and unified sections; reports position-aware parse errors.
3. **Hunk model:** compact representation of coordinates and line types; optionally stages large hunks in a temporary file rather than RAM.
4. **Matcher/application engine:** leverages Wall's original functionality where possible; exact context matches initially, bounded search/fuzz later.
5. **DOS file/transaction adapter:** path validation, safe temporary output, replacement, recovery, file attributes and errors.
6. **Diagnostics and exit status:** fixed-string and integer output only.

Keep the format parser distinct from the application engine so unified diffs can be added without importing later GNU parsing code or unnecessarily rewriting Wall's matcher.

## 5. Initial user interface

Illustrative commands (final option syntax can change after examining Wall's original CLI):

```dos
PATCH16 -p1 < UPDATE.PAT
PATCH16 SOURCE.C UPDATE.PAT
PATCH16 -n -p1 < UPDATE.PAT
PATCH16 -o RESULT.C SOURCE.C UPDATE.PAT
```

Proposed options:

| Option | Meaning |
|---|---|
| `-pN` | Strip N leading path components from patch header paths. |
| `-n` / `--dry-run` | Verify patch applicability without modifying target files; actual long-option support is optional. |
| `-o FILE` | Write patched result to another file, without replacing original. |
| `-d DIR` | Choose a working root (if feasible with DOS path semantics). |
| `-R` | Reverse patch (later milestone unless inherited cleanly). |
| `-F N` | Maximum context fuzz (deferred; start at zero). |

For scripts, use predictable exit codes: `0` all hunks applied; `1` any hunk rejected or patch not applicable; `2` usage, I/O, malformed input, memory, or other fatal error. Confirm compatibility with Wall's historical behavior before freezing the interface. Never claim success if an input file cannot be replaced safely.

## 6. Patch formats and compatibility

### Unified diffs — required

Implement ordinary textual unified format:

```diff
--- a/HELLO.C
+++ b/HELLO.C
@@ -1,2 +1,3 @@
 first
+new
 second
```

Requirements:

- Parse `---`/`+++` file headers and `@@ -start[,count] +start[,count] @@` hunk headers, including omitted counts (meaning one), zero-length ranges, and optional trailing section labels.
- Preserve meaning of context (` `), addition (`+`), and deletion (`-`) lines.
- Support multiple hunks and multiple files per input where representable on DOS.
- Support `\ No newline at end of file` markers correctly for source and target files; never silently invent a newline.
- Recognize harmless Git textual preamble (`diff --git`, `index`, etc.) **without** attempting to apply binary or mode-only changes. Reject unsupported transformations clearly.
- Validate counts, ordering, overflow, and expected locations before any commit.
- Handle `/dev/null` create/delete semantics only after safe file-creation and deletion transactions are designed and tested.

### Original formats

Inventory and test the formats supported by the specific Wall baseline. Preserve **context diff** and **normal diff** where practical. Do not let preserving an obscure original option compromise unified-format reliability or memory safety.

### Matching policy

Start with **exact context** and no fuzzy matching. If Wall's engine already supports bounded offsets/fuzz, document and test it explicitly; otherwise defer fuzz as a separate enhancement. Never apply an ambiguous hunk without an explicit, deterministic policy. Reject overlapping hunks and impossible offsets with useful diagnostics. Investigate already-applied/reversed-patch detection separately.

## 7. DOS-specific text, paths, and transactional file operations

### Line endings and EOF

- Accept LF and CRLF on patch input, including a patch file created on Linux and transferred without conversion.
- On target files, treat LF and CRLF as line separators for matching but **preserve existing target line endings** when writing output by default; define behavior for mixed-ending files.
- Preserve the distinction between a last line with and without a terminating newline.
- Define an explicit policy for DOS text EOF marker `^Z` (`0x1A`): never silently discard bytes in arbitrary files. Document any opt-in DOS text treatment rather than treating `^Z` as universal EOF.
- Reject NUL-containing binary input in v0.01 or require a deliberately chosen text/binary policy; do not produce corrupted output silently.
- Treat code-page bytes as opaque bytes except ASCII diff syntax; no UTF-8 decoding requirement on the DOS host.

### DOS filenames and directory traversal

- Recognize `/` and `\` separators where appropriate for patch paths, strip `a/` and `b/` prefixes with `-p1`, and enforce 8.3 names for the target DOS filesystem.
- Do **not** truncate long filenames or silently alias distinct paths.
- Reject absolute paths, drive-qualified paths from untrusted patches, `..` traversal escaping the chosen root, device names, and unsafe redirections. Keep all writes within an explicitly chosen working root.
- Consider case-insensitive path matching according to the target filesystem, not host assumptions. Check filename collisions after DOS normalization.

### Safe replacement

A first-pass workflow for each file:

1. Open the original read-only.
2. Create an unpredictable or collision-checked temporary file **on the same DOS drive and preferably in the same directory**.
3. Apply every hunk to the temporary output; validate source consumption and resulting output.
4. Flush/close and check all I/O errors.
5. If the operation is applicable and requested, make a recoverable backup/rename of the original, move temporary output into place, and restore the original on any failure if possible.
6. Retain a diagnostic and recovery instructions if rollback itself fails; never silently delete the only recoverable original.

DOS 3.x rename semantics, attribute handling, replacement behavior, and failure windows require explicit experiments. **Do not claim POSIX-style atomic replacement**: DOS lacks the same guaranteed rename-over-existing-file semantics. Multi-file patches cannot be promised to be globally atomic; define per-file commits, partial-success reporting, and recovery policy. A failure halfway through a multi-file patch must not be reported as complete success.

## 8. Memory and performance strategy

The key constraint is **conventional memory**, not just file size. Under DOS, program code, data, stack, heap, and temporary buffers compete for a limited address space.

- Audit Wall's assumptions about in-core line indexes, dynamically growing arrays, fixed-width integers, `malloc` patterns, and temporary-file paths before selecting the memory model.
- Favor **streaming or file-backed storage** for source-file line indexes and hunk data; maintain a bounded in-memory working set. Seek within the source file instead of retaining every line if that meets performance requirements.
- If an original algorithm needs memory proportional to input size, retain the historical algorithm only under a documented input cap, or replace that component with an independently written bounded-memory equivalent and document the deviation.
- Bound individual line length and in-memory hunk size; fail clearly before output replacement if the cap is exceeded. Consider on-disk staging for large hunks as a later improvement.
- Report measurable peak conventional memory, executable size, and runtime on representative 8088-class configurations and floppy/hard-disk images.
- Optimize for correctness and predictable failure before micro-optimizing for 8088 speed.

## 9. Test strategy

### Host-side differential tests

Generate known old/new text pairs on Linux. Use modern `diff -u` (and ordinary text patches from Git) as **format producers** and GNU `patch` as an optional black-box oracle, not as copied source. Compare output bytes after applying the documented newline policy.

Test:

- Empty, one-line, and very large files; single and multiple hunks.
- Insertions/deletions at beginning, middle and end; zero-count hunk ranges.
- Missing final newline on either side.
- LF, CRLF, and mixed line endings; trailing `^Z` edge cases.
- Repeated context, ambiguous matches, shifted line numbers, and wrong original content.
- Malformed patch syntax, overflow, excessive lengths, and truncated input.
- Multiple files, `-pN`, 8.3 conflicts, path traversal, device names, and unsupported Git operations.
- Disk full, write errors, read-only attributes, missing paths, rename failure, and temp-file collisions.
- Dry runs and failed hunks leave the original file unchanged.
- Text patches whose output is larger than available DOS conventional memory.

### DOS execution and integration

- Build and execute with DOSBox-X for fast unit/behavior tests; use QEMU for reproducible GR-DOS integration tests, with all modifications confined to disposable images.
- Test on MS-DOS-compatible environments as a cross-check where available.
- Test at least one original 8088/8086 environment or a suitably accurate emulation configuration; verify instruction compatibility, not merely successful execution under a 386-class emulator.
- Provide an integration fixture: create a source file on Linux, generate `diff -u`, put the old file and patch on a GR-DOS floppy/hard-disk image, run `PATCH16`, and verify the resulting file byte-for-byte after normalized/newline-aware comparison.
- Add tests for avoiding proprietary runtime linkage and regression checks for `libc16` integration across the selected model.

## 10. Exploration milestones and release gates

| Stage | Deliverable | Gate |
|---|---|---|
| **E0: Source and rights** | Original archive, checksums, notices, early GNU GPL evidence, contributor inventory | **Verified GPL license grant for the chosen baseline**; otherwise stop importing original code |
| **E1: Port feasibility** | Build report, Unix dependency inventory, DOS memory-model choice, `libc16` API gap list | No hidden proprietary runtime dependencies; viable 8086 build |
| **E2: Core patching** | Basic Wall-format patching of DOS text files | Tests for correctness, disk full, and recoverable replacement |
| **E3: Unified format** | Independently implemented unified parser and Git-text compatibility | Linux-to-GR-DOS round-trip corpus passes |
| **E4: Robustness** | DOS path safety, explicit newline policy, bounded memory, rejected hunks | Failure modes do not silently corrupt source files |
| **E5: Release** | Binary, source, license texts, provenance, manual, tests, GR-DOS packaging guidance | CI/test matrix passes; legal and provenance gates complete |

A practical **v0.01** may ship only after E0–E4 are met, with clearly documented format, size, and option limitations. A read-only feasibility prototype can precede license resolution, but **do not publish or redistribute a Wall-derived binary or combined-source artifact until the GPL grant is established**.

## 11. Distribution and documentation

Suggested repository layout:

```text
patch16/
  README.md
  LICENSES/                 # verified GPL text; other applicable grants
  docs/
    DESIGN.md
    HISTORY-LICENSE.md     # original notice in context, if appropriate
    LICENSE-RESEARCH.md    # source evidence and legal open questions
    PROVENANCE.md          # origins of each source module
    DOS.md                 # installation, CLI, format and DOS caveats
  upstream/                 # pristine archive or manifest, only if redistribution is authorized
  src/                      # adapted Wall source and new modules
  compat/                   # DOS I/O/path/transaction adapters
  tests/
  Makefile
```

The release must explicitly distinguish **Wall's authorship**, later project contributors, the **operative GPL license**, historical permission language (if included), and the **MIT license of `libc16`**. Packaging with GR-DOS should keep source and license obligations visible and should not imply that all bundled executables share GR-DOS's MIT license.

## 12. Open questions

1. What is the earliest primary-source GNU license notice establishing GPL rights to Wall's original code, and what exact GPL versions does it authorize?
2. Does the chosen 1988 archive contain anything not authored or licensed by Wall on the same terms?
3. Can the original noncommercial notice be offered as a genuine **whole-program** alternative once DOS and unified-diff changes are included, or should it remain purely historical?
4. What Unix assumptions in Wall's exact source are most expensive to port (signal handling, `stdio`, temp files, memory, directories, filename parsing)?
5. Which `libc16` features are genuinely missing, and which are better implemented as local DOS adapters?
6. Which memory model yields an acceptable executable and runtime footprint on an original PC/XT?
7. What is the minimum sensible unified-diff compatibility surface for source files generated by GNU `diff` and Git?
8. How should DOS `^Z`, mixed line endings, and file-creation/deletion patches behave by default?
9. Can safe per-file replacement and recovery be demonstrated on actual DOS filesystems, including full disks and read-only files?

---

**Decision summary:** pursue Wall's 1988 `patch` as the preferred technical and historical baseline; **require a verified GPL license** before distributing any derivative; treat his original restrictive permission as a potential alternate grant **only if rights are verified for the complete modified work**, otherwise preserve it solely with historical context. Implement unified-diff support and DOS-specific extensions from permitted MIT/GPL/Wall code where suitable, otherwise clean-room; keep `libc16` additions MIT-only, avoid `*printf`, and exclude Schilling-authored code.
