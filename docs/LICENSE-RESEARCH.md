## 3. Contents and contributors

### 3.1 Files

The 20 files listed in Wall's `MANIFEST` are Wall's kit. The other five were added or generated by the X distribution:

| File | Origin | Used by the build? |
|---|---|---|
| `CHANGES` | X Consortium note: "a more recent version has been supplied" (since R2) | no |

`malloc.c` has unknown terms and isn't compiled, so it is excluded from `patch16` outright. `libc16`'s `malloc` replaces it.

`util.c` is the only C file without an RCS `$Header$`. GNU `patch` 2.1's `util.c` has none either, so this comes from Wall's distribution and is not an X edit.

The practical risk is small, since the changes are 1984–85 contributions merged into Wall's code and redistributed under the GPL by the FSF for decades. It still has to be recorded as an assumption, not as verified.

Primary source: the GNU `patch` repository, `https://git.savannah.gnu.org/git/patch.git`. Tags `v2.1` through `v2.5.9` are imports of the release tarballs, made by Andreas Gruenbacher in March 2009. Only license notices, READMEs, NEWS and ChangeLogs were read; no code was taken.

## 5. Assessment against DESIGN.md §3.2

What is established:

1. From 1997 at the latest, the FSF states that Wall agreed to GPL distribution of GNU `patch`, and labels Wall's 1984–1988 copyright **GPL version 2 or any later version**.
2. The FSF published Wall's code with GPLv2 `COPYING` from 1993 (2.1). It did so under its own GPLv2-or-later notices for every file from 1997 (2.2), and has done so continuously since.

What is not established:

| Gap | Why it matters |
|---|---|
| G1. No statement in Wall's own words | The grant is reported by the FSF, not quoted. |
| G2. Scope: "GNU \`patch'" | Does the permission cover the 1988 snapshot as used independently by `patch16`, or only distribution of the GNU package? (§3.2, bullet 2) |
| G3. Version and "or later" | The "version 2, or (at your option) any later version" wording is the FSF's standard notice. Nothing shows whether Wall chose the version and the "or later" option. Wall's agreement is undated, so it could be before or after GPLv2 (June 1991). |
| G4. Timing | 2.1 (1993) shipped GPL `COPYING` while still carrying Wall's restrictive headers. The explicit grant statement appears only in 1997. |
| G5. Contributors (§3.2) | Van Jacobson, jromine and joe@fluke changes, plus the patch10 `-B` contributor. |
| G6. Original 2.1/2.2 tarballs | Only the 2009 git imports were examined. |

**Gate status: not met.** The evidence is good, but it isn't the complete chain of title DESIGN.md §3.2 requires before importing Wall's code into `patch16` for distribution.

## 6. Ways to close the gate (superseded by §8)

This section is kept for the record. The project chose option 3 (§8), so contacting Wall or the FSF is no longer a prerequisite. Seek clarification only if a real ambiguity remains for a file that is needed.

In order of strength:

1. **Ask Larry Wall directly.** Request written confirmation that his patch 2.0 (patchlevel 12) may be modified and redistributed under GPL-2.0-or-later. Ideally the confirmation also says whether the original notice may be offered as an alternative (DESIGN.md §3.3, Option A). This closes G1–G4 at once; G5 remains an assumption. It is the route §3.2 names ("seek explicit permission").
2. **Locate the original GNU 2.2 release tarball and any FSF copyright-assignment or permission record.** The FSF copyright clerk keeps a records file; `copyright-clerk@fsf.org` can say whether a disclaimer or permission from Wall for `patch` is on file. This closes G6 and possibly G1 and G3.
3. **Rebase onto a GPL-labeled Wall baseline:** GNU `patch` 2.2's files, whose headers carry Wall's copyright under GPLv2-or-later. This is the "separately verifiable Wall-code baseline under the GPL" in §3.2. The cost is that it brings in roughly 1989–1997 FSF changes, including Wayne Davison's unified-diff support, the very GNU code §3.1 says not to import "by accident". DESIGN.md E3 expects an independent unified parser. Taking this route would need a deliberate design change.

**Recommendation:** pursue (1) and (2) in parallel. Meanwhile, E1 can continue as a local, unpublished feasibility study (DESIGN.md §10), which is how it was done (PORT-FEASIBILITY.md). Until then, prefer GPL-2.0-or-later as the provisional identifier; don't publish it.

## 7. Treatment of Wall's notice (DESIGN.md §3.3)

Option B (historical artifact) remains the default. Option A would need Wall's agreement for the modified program **and** grants from the §3.2 contributors, which is unlikely to be obtainable for every part. `docs/HISTORY-LICENSE.md` should reproduce the two notices in §2 verbatim as historical context, with their source path and the SHA-256s from `upstream/x11r3-patch-2.0pl12.sha256`, and state that the operative license is GPL-2.0-or-later (§8).

## 8. Baseline: GNU `patch` 2.2 (decision 2026-10-28)

Decision (PR #1, https://github.com/gr-dos/patch16/pull/1#issuecomment-6468026597): `patch16` is based on **GNU `patch` 2.2, distributed under its published "GPL version 2, or (at your option) any later version" terms**. This replaces porting the independently distributed 1988 snapshot. Consequences:

- `patch16` is distributed under **GPL-2.0-or-later**.
- Wall's 1988 noncommercial notice is **historical context only** (§7, Option B). It is not offered as an alternative license for the modified program.
- Later GNU `patch` releases published under GPLv2-or-later (through 2.5.9) are also eligible sources for specific changes. Each reuse is recorded in PROVENANCE.md. GPLv3-only releases (2.6 onward) are not used.
- `libc16` remains MIT-only. Nothing from this lineage goes into it.
- No Jörg Schilling-authored code: the 2.2 tree contains no file or ChangeLog entry by him (searched for "Schilling" and "Joerg").
